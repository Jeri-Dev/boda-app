# boda-app — conventions

PWA to manage a single wedding. **The app is open — there is NO authentication.** Two surfaces, one database:

- **Back-office** (`(host)` route group) — wedding management (guests, budget, vendors, tasks, tables, floor plan). Lives at the app root `/`. `robots: noindex`. Access control, if any, is at the deployment layer (private URL, password-protected hosting, local use) — never in the app.
- **Guest-facing** (`(public)` route group) — `/i/[token]` invitation + RSVP, `/info` web + gift registry, `/~offline` fallback.

Stack: Next.js 16 (App Router, React 19) · **Drizzle ORM + Supabase Postgres** (server-side via `postgres.js`) · Tailwind v4 (CSS-first, no `tailwind.config.ts`) · Zod 4 · Vitest + pglite · Playwright · pnpm.

## Data layer (Drizzle + Supabase Postgres)

- **One client:** `src/lib/db/index.ts` (`import 'server-only'`) exports `db` (Drizzle + `postgres.js`). The browser **NEVER** touches the DB. Same code dev/prod — only `DATABASE_URL` (a Postgres connection string) changes. `prepare: false` is set for Supabase's transaction pooler (serverless). NEVER prefix `DATABASE_URL` with `NEXT_PUBLIC_`.
- **Schema** in `src/lib/db/schema.ts` (`pg-core`). Constrained columns: `text({ enum: [...] })` + a SQL `check()` (type-safe in TS *and* enforced in Postgres). Timestamps are `timestamptz` (Drizzle returns/accepts `Date`); `$onUpdate` refreshes `updated_at`. **Real FKs** (`on delete cascade`/`set null`) own referential integrity — do NOT re-add manual soft-ref cleanup on delete.
- **Atomic multi-statement ops use `db.transaction(async (tx) => …)`** — not `db.batch` (that was libSQL-only).
- **Migrations** in `src/lib/db/migrations/` are generated by `pnpm db:generate` and committed (incl. `meta/_journal.json`); the initial one also enables **RLS deny-by-default**. Apply with `pnpm db:migrate` (runs the SQL incl. RLS; `db:push` would skip it). NEVER run migrations inside the serverless runtime — a separate deploy step against a direct/session connection.
- **Security posture (open app, no auth):** the primary control is that only the server holds `DATABASE_URL` and Supabase's public Data API is **disabled**. RLS deny-by-default (enabled, zero policies, no `FORCE`) is defense-in-depth. Back-office access is gated in two layers: the path-based `netlify/edge-functions/basic-auth.ts` (required) AND — because Server Actions are dispatched by action-ID, not route, so a POST to a public `/i/…` path can invoke one — every back-office action calls `requireBackofficeAuth()` (`src/lib/auth/backoffice.ts`) first. The public `submitRsvp` is the only exempt action. See `docs/deploy-netlify.md`.

## Next.js 16 reminders

- `cookies()` / `params` are async (await them). `redirect()` throws — call it **outside** try/catch.
- Read `node_modules/next/dist/docs/01-app/` before touching routing. Avoid `'use cache'`.
- Server Action recipe (no auth gate): `'use server'` → `Schema.safeParse` → mutate via `db` → `revalidatePath` → `redirect()` outside try/catch.

## Local dev

- `pnpm dev` — app. `pnpm db:generate` — generate a migration from `schema.ts`. `pnpm db:migrate` — apply to the Postgres in `DATABASE_URL`. `pnpm db:studio` — Drizzle Studio. `pnpm test` — Vitest (unit + RSVP security on pglite, no Docker).
